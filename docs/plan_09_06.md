# Plan Architektury SignalTrack V1

## 1. Cel planu

Ten plan opisuje docelowy kierunek przebudowy architektury SignalTrack zgodnie z `SDD.md` oraz rozmowa projektowa z 09.06.

Najwazniejsza zmiana: system ma byc zbudowany wokol pojedynczej proby pomiarowej:

```text
trial_id + target_time + phase_map + amplitude_map + metrics
```

Kazdy TX, RX, FSV i SystemController musi konsekwentnie pracowac na tym samym `trial_id`. Dzieki temu mozna bezpiecznie skladac wyniki, wykrywac bledy koordynacji i rozwijac beamforming bez mieszania prob.

## 2. Model wdrozenia

- Ten sam kod jest wdrozony na kazdym node z USRP B210.
- Node sa w tej samej sieci Wi-Fi i komunikuja sie przez MQTT.
- Jeden wybrany komputer uruchamia `SystemController`.
- Kazdy node uruchamia proces z jawna rola i ID:

```bash
python main.py system --config config.yaml
python main.py tx 0 --config config.yaml
python main.py tx 1 --config config.yaml
python main.py rx 0 --config config.yaml
python main.py rx 1 --config config.yaml
```

- Ten sam wspolny YAML znajduje sie na kazdym node.
- Proces wybiera swoja sekcje na podstawie `role + id`, np. `tx 1` czyta `nodes.tx["1"]`.
- `SystemController` czyta caly config: MQTT, liczbe node, targety, sweep, timing, synchronizacje i tryb beamformingu.

## 3. Wspolny YAML i walidacja node

Przykladowy ksztalt configu:

```yaml
mqtt:
  broker: 192.168.8.126
  port: 1883

timing:
  trial_lead_time_s: 1.5
  trial_timeout_s: 4.0
  pre_trigger_s: 0.01
  capture_time_s: 0.1

nodes:
  tx:
    "0":
      serial: "3273ABF"
      external_clock: true
      external_time_source: true
    "1":
      serial: "3273ACB"
      external_clock: true
      external_time_source: true

  rx:
    "0":
      serial: "3273AF9"
      external_clock: true
      external_time_source: true
    "1":
      serial: "3273AC0"
      external_clock: true
      external_time_source: true

targets:
  tc1:
    rx_id: "1"

beamforming:
  mode: optimize
  target: tc1
  geometry: linear
  tx_array_order: ["0", "1", "2", "3"]
  tx_antenna_spacing_lambda: 0.5
  scan_angles_deg: [-60, -45, -30, -15, 0, 15, 30, 45, 60]
  repeats_per_angle: 3
  tx_signal_amplitude: 0.7

calibration:
  enabled: true

fsv:
  enabled: true
  capture_every_trial: true
  required_for_beamforming: false
```

Walidacja przy starcie:

- `tx <id>` czyta tylko `nodes.tx[id]`.
- `rx <id>` czyta tylko `nodes.rx[id]`.
- Proces inicjalizuje USRP po serialu z configu albo sprawdza wykryty serial.
- Jesli faktyczny USRP nie pasuje do `role + id`, proces przechodzi w blad i nie wysyla `READY`.
- `SystemController` startuje eksperyment dopiero, gdy wszystkie wymagane TX/RX wysla `READY`.
- W `test_mode` walidacja seriala moze byc pominieta albo symulowana.

## 4. Stany eksperymentu

`SystemController` powinien prowadzic jawny stan:

```text
WAITING_FOR_COMPONENTS
SYNCING_CLOCKS
READY_TO_MEASURE
ARMING_TRIAL
WAITING_FOR_RESULTS
PROCESSING_RESULTS
FINISHED
ERROR
```

Podstawowy flow:

1. TX/RX/FSV wysylaja `REGISTER`.
2. TX/RX inicjalizuja sprzet i synchronizacje.
3. TX/RX wysylaja `READY`.
4. System wysyla `SYNC_CLOCKS`.
5. Node uzbrajaja zerowanie czasu na PPS.
6. System wysyla `START`.
7. System wykonuje kolejne proby `trial_id`.

## 5. Synchronizacja i target_time

- `target_time` oznacza czas sprzetowy USRP, a nie luzny czas PC.
- W trybie sprzetowym TX i RX korzystaja z PPS oraz 10 MHz zgodnie z ustawieniami w YAML.
- Ustawienia `external_clock` i `external_time_source` sa definiowane osobno dla kazdego node.
- System planuje probe z konfigurowalnym zapasem, np. `trial_lead_time_s: 1.5`.
- Jesli TX/RX dostanie komende za pozno, proba dostaje status `FAILED`.
- Niekompletna albo spozniona proba jest logowana, ale nie aktualizuje beamformingu.

## 6. Protokol MQTT

Envelope zostaje prosty:

```json
{
  "src": "system",
  "id": "0",
  "cmd": "TX_PULSE",
  "payload": {},
  "timestamp": 0.0
}
```

Wiadomosci pomiarowe musza zawierac `trial_id`.

### RX_CAPTURE

```json
{
  "cmd": "RX_CAPTURE",
  "payload": {
    "trial_id": 15,
    "target_time": 12.5,
    "pre_trigger_s": 0.01,
    "capture_time_s": 0.1
  }
}
```

### TX_PULSE

```json
{
  "cmd": "TX_PULSE",
  "payload": {
    "trial_id": 15,
    "target": "tc1",
    "target_time": 12.5,
    "beam_angle_deg": 30.0,
    "phase_map": {
      "0": 0.0,
      "1": 1.57079632679,
      "2": 3.14159265359,
      "3": 4.71238898038
    },
    "amplitude_map": {
      "0": 0.7,
      "1": 0.7,
      "2": 0.7,
      "3": 0.7
    }
  }
}
```

### RX_METRIC

```json
{
  "cmd": "RX_METRIC",
  "payload": {
    "trial_id": 15,
    "rx_id": "1",
    "target_time": 12.5,
    "power_linear": 0.000031,
    "power_db": -45.08,
    "detected_time": 12.500214,
    "offset_ms": 0.214,
    "samples_used": 1000
  }
}
```

### TX_DONE

```json
{
  "cmd": "TX_DONE",
  "payload": {
    "trial_id": 15,
    "target_time": 12.5,
    "samples_requested": 32768,
    "samples_sent": 32768,
    "late": false
  }
}
```

Migracja nazw:

- `RX_PULSE` -> `RX_CAPTURE`
- `METRIC` -> `RX_METRIC`
- `TX_ACTIVE` -> `TX_DONE`

Stare handlery moga zostac tymczasowo jako compatibility shim z ostrzezeniem w logu.

## 7. Tryby beamformingu V1

### optimize

Tryb `optimize` szuka najlepszego kata/fazy dla wybranego targetu, np. `tc1`.

- `tc1` jest aliasem na fizyczny RX, np. `tc1 -> rx_id: "1"`.
- System testuje liste katow z YAML.
- Dla kazdego kata liczy `phase_map` z geometrii liniowej.
- Dla kazdego kata wykonuje `repeats_per_angle` prob.
- Decyzja jest oparta o srednia moc liniowa `power_linear` z RX przypisanego do `tc1`.
- Nie usredniamy decyzyjnie w dB.
- Po przejsciu listy katow system wybiera kat z najwieksza moca dla targetu.

### scan

Tryb `scan` stale omiata wiazka po liscie katow.

- System cyklicznie przechodzi po `scan_angles_deg`.
- Dziala do `STOP` albo przerwania procesu.
- Kazdy kat ma wlasne `trial_id` i log.
- FSV oraz RX moga pokazywac, jak moc zmienia sie podczas omiatania.
- Scan nie musi wybierac jednej najlepszej fazy.

## 8. Geometria anten

V1 obsluguje liniowy szyk TX.

Dla kata `theta`:

```text
phase_step = -2 * pi * d/lambda * sin(theta)
TX0 = 0 * phase_step
TX1 = 1 * phase_step
TX2 = 2 * phase_step
TX3 = 3 * phase_step
```

`tx_array_order` musi odpowiadac fizycznej kolejnosci anten. Jesli fizyczny uklad jest inny niz config, wiazka pojdzie w zlym kierunku.

Pelne skanowanie 360 stopni nie jest celem V1. Do realnego 360 potrzebna jest inna geometria, np. szyk kolowy albo planarny, oraz osobna kalibracja.

## 9. RX metrics

W V1 RX zawsze odsyla metryke z okna pomiarowego, nawet jesli maksimum moze byc szumem.

Konsekwencje:

- Implementacja jest prostsza.
- Algorytm moze optymalizowac szum, jesli impuls nie jest widoczny.
- Dlatego kalibracja TX0..TX3 jest domyslnie wlaczona.
- W kolejnej wersji mozna dodac `pulse_found`, progi mocy, maksymalny offset i SNR.

## 10. Kalibracja

Kalibracja jest opcjonalna, ale domyslnie wlaczona.

Minimalna kalibracja:

1. Uruchomic TX0 samodzielnie.
2. Sprawdzic, czy RX widza impuls.
3. Powtorzyc dla TX1, TX2, TX3.
4. Zapisac poziomy mocy i offsety czasowe.
5. Opcjonalnie zapisac diagnostyke FSV.

Jesli kalibracja nie przejdzie:

- w trybie domyslnym system loguje blad i nie rozpoczyna beamformingu,
- config moze pozwolic na kontynuacje mimo ostrzezen.

## 11. Rola FSV / analizatora

FSV jest diagnostyka, nie glownym optymalizatorem.

- FSV mierzy kazda probe, jesli `capture_every_trial: true`.
- FSV nie blokuje beamformingu, jesli `required_for_beamforming: false`.
- FSV pokazuje sygnal w swoim punkcie pomiarowym: moc, widmo, impuls i ewentualnie faze.
- FSV nie pokazuje sam z siebie pelnej mapy wiazki przestrzennej.
- Mapa wiazki wymaga wielu RX albo przesuwania anteny pomiarowej i logowania mocy wzgledem pozycji/kata.

## 12. CSV i logowanie

Jeden wiersz CSV powinien oznaczac jedna probe `trial_id`.

Minimalne pola:

- `trial_id`
- `target_time`
- `status`
- `beamforming_mode`
- `target`
- `target_rx_id`
- `beam_angle_deg`
- `phase_map`
- `amplitude_map`
- metryki RX
- statusy TX
- flagi late command
- dane FSV, jesli dostepne
- informacja, czy proba aktualizowala beamforming

Nie nalezy laczyc wynikow wielu prob w jednym wierszu bez jednoznacznego `trial_id`.

## 13. Pytesty

Pytesty maja sens dla logiki i koordynacji, nie dla fizyki RF.

Zakres testow unit:

- parsowanie YAML,
- wybor sekcji po `role + id`,
- walidacja `tc1 -> rx_id`,
- walidacja seriala USRP przez adapter/mock,
- konwersja stopnie -> radiany,
- angle -> `phase_map` dla linear array,
- state machine `trial_id`,
- timeout proby,
- ignorowanie niekompletnej proby,
- wybor najlepszego kata po `power_linear`,
- format wiadomosci MQTT.

Zakres testow integration w `test_mode`:

- fake system + fake TX/RX,
- rejestracja node,
- sync/start,
- kilka prob,
- kompletne CSV,
- brak aktualizacji beamformingu po failed trial.

Testy manualne hardware:

- PPS i 10 MHz zgodnie z configiem,
- kazdy node ma poprawny serial,
- kazdy `trial_id` ma jedna pare `RX_CAPTURE`/`TX_PULSE`,
- RX widzi impuls blisko `target_time`,
- scan zmienia mierzona moc,
- optimize wybiera powtarzalny najlepszy kat dla `tc1`,
- FSV pokazuje diagnostycznie impuls i zmiany mocy.

## 14. Kolejnosc implementacji

1. Dodac loader YAML z fallbackiem do `helpers/parameters.py`.
2. Dodac modele/protokol wiadomosci i stale komend.
3. Dodac `trial_id` i state machine w `SystemController`.
4. Zmienic `RX_PULSE` na `RX_CAPTURE`, `METRIC` na `RX_METRIC`, `TX_ACTIVE` na `TX_DONE`.
5. Dodac walidacje node po `role + id + serial`.
6. Dodac planowanie `target_time` z `trial_lead_time_s`.
7. Przebudowac beamforming na `optimize` i `scan`.
8. Dodac kalibracje TX po kolei.
9. Podlaczyc FSV jako diagnostyke per trial.
10. Dodac pytesty i test-mode integration.

## 15. Otwarte ryzyka

- Jesli `tx_array_order` nie odpowiada fizycznym antenom, scan/optimize beda dawac mylace wyniki.
- Jesli RX nie widzi impulsu, tryb `Always Metric` moze optymalizowac szum.
- Jesli FSV mierzy kazda probe i jest wolny, musi dzialac asynchronicznie, zeby nie blokowal glownego cyklu.
- Pelne omiatanie wokol ukladu nie jest realistyczne dla prostego liniowego szyku bez niejednoznacznosci kierunku.
